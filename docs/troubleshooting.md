# 通用排查手册：跑步机 / 走步机连不上、没反应、数据不对

这份文档按「症状」组织，不按「型号」组织。所以你手上是别的品牌、别的型号也能照着走——每一步都写了怎么判断、判断完往哪走。文中标注「推测」的是还没定位到根因的，别当结论用。

## 先记住四条原则

1. **分层判断**：机器本体 → 实体遥控 → 连接层（蓝牙/红外/射频）→ 协议层 → 应用层。五层里任何时候只有一层是坏的，别跳层猜。
2. **一次只改一个变量**：同时换手机、换 App、换位置，最后你不知道是哪一步修好的。
3. **先定性再定量**：先确认「能不能动」「有没有数据」，再去纠结数值准不准。
4. **留记录**：同一个现象记下型号、手机型号、系统版本、操作步骤、结果，否则第二次遇到还得从头来。

---

## 症状 1：按了没反应

先分清是哪一层没反应，这三条是独立链路，一个没好不代表另一个坏：

- **面板按钮**没反应 → 机器本体或供电问题，与遥控和 App 无关
- **实体遥控器**没反应 → 发射端 / 接收端 / 电池
- **App 里按了**没反应 → 连接层或协议层

排查顺序：

1. 先用面板启动，确认机器本身正常。面板也不行，直接查电源、安全锁、急停夹是否到位。
2. 判断遥控类型：**手机摄像头对着遥控器发射头按一下**，屏幕上看到紫白色闪烁＝红外；什么都看不到，多半是射频或蓝牙。
3. 红外型：换电池 → 看发射管是否闪 → 用万能遥控类应用试码库 → 仍不行，考虑接收窗口被遮挡或脏污。
4. 射频型：确认频段（433 / 315 MHz 等）与编码方式（固定码 / 滚动码），滚动码对拷成功率低。
5. 蓝牙型：见症状 2 与症状 3。

> 我们自己的机器上出现过「实体遥控器完全无反应，但机器本体正常」的情况，最后判定在遥控链路，软件层修不了——这种要先定性，别在 App 里反复改代码。

---

## 症状 2：手机搜不到设备

按这个顺序排，命中率从高到低：

1. **权限**：安卓上蓝牙扫描常需要「附近设备」权限，部分机型还要求打开**定位开关**（不只是定位权限）。
2. **设备没在广播**：有些机器需要先在面板上按一下、或拉动安全锁后才进入可连接状态。
3. **被别的手机占用**：上次连过的手机还在附近且连着，新手机搜不到。
4. **距离与遮挡**：贴着面板试，别隔着人。
5. **名称过滤写错**：如果代码里按名称前缀过滤，先打印全量扫描结果看实际广播名，别猜。

> 教训：按设备名前缀自动识别设备时，一定要先把扫描到的**全部**名称打印出来看一眼。名字里带空格、大小写不一致、或带固件后缀，都会让过滤条件失效。

---

## 症状 3：连上了，但没有数据

这是最常见的一类，按顺序试：

1. **读错了方式**：很多设备的运动数据是**订阅（notify/indicate）**才会持续推送，用「读取」拿到的永远是空或初始值。
2. **缺握手/唤醒**：部分机型需要先往某个特征值写一条唤醒或握手指令，才开始上报。
3. **特征值选错**：同一设备可能有多个相似的服务，逐个订阅，看哪个有变化。
4. **单位换算**：原始值常是 0.1 km/h、0.01 km、或需要除以 10/100，先按「速度会不会离谱」判断单位对不对。
5. **一机一连接**：有些设备只允许一个客户端，旧连接没释放就再也读不到。

---

## 症状 4：能读到数据，但控制不了

数据和控制在协议里通常是两条独立的通道，能读不代表能写：

1. 确认控制指令走的是**写（write/write-without-response）**，不是读。
2. 检查是否要求**顺序下发**（先进入手动模式，再给速度）。
3. 检查是否带校验位/累加和/序列号，很多指令是「一帧一校验」，改了速度值没重算校验就会被丢弃。
4. 检查速度限制：多数机器有最低启动速度和步进档位，直接发 0.1 km/h 会被忽略。

---

## 症状 5：暂停后计时被重置（我们真实踩过的坑）

**现象**：训练中暂停，继续时计时从头开始，之前累计的时间丢了。

**后果**：一次 30 分钟的训练只记到后半段，周报、累计天数、连续天数全部失真。

**根因方向**（常见实现，未逐行确认）：暂停时销毁了计时器实例，恢复时重新创建，初始值没从上次状态取；或者暂停把「已用时长」存进临时变量，恢复走了另一条不读它的路径。

**修法**：不要用「计时器实例」承载时长，改成**状态 + 时间戳**：

- 记 `startedAt`、`pausedTotal`、每次暂停的起止
- 当前时长恒为 `now - startedAt - pausedTotal`
- 暂停/恢复只改状态，不重建对象

**回归用例**（照着写一条测试）：开始 → 跑 60 秒 → 暂停 10 秒 → 恢复 → 再跑 60 秒。期望：有效时长 120 秒、暂停 10 秒、总时长 130 秒。

---

## 症状 6：数据对不上（里程、时长、卡路里）

先分清是「算法错」还是「口径错」，多数是后者：

1. **墙上时间 vs 有效时长**：含暂停的总时间不是运动时长，统计必须用有效时长。
2. **跨零点**：23:50 开始、00:20 结束，算哪天？定死「按开始日归日」，否则周报天天对不上。
3. **卡路里**：设备上报的、公式估算的、和 App 自己算的经常差一截，必须在数据里标 `source`，别混着统计。
4. **采样丢包**：断连期间速度按最后一次值积分，会虚高；断连超过阈值应显式标记为缺失，不要平滑填补。

---

## 症状 7：用一会儿就断连

1. 省电策略把 App 在后台杀掉 → 加前台服务或白名单（这一步各家 ROM 差异很大）。
2. 蓝牙与 Wi-Fi（尤其 2.4G）互扰 → 换 5G Wi-Fi 或挪开路由器试。
3. 重连策略缺失 → 断连后要指数退避重试，而不是放任不管，否则用户以为「App 坏了」。
4. 通知/订阅被系统回收 → 重连后必须**重新订阅**特征值，很多人只重连不重订阅。

---

## 症状 8：语音播报不响 or 说到一半被打断

1. 音频焦点：来电、导航、其他媒体的焦点抢占，播报会被静默丢弃。
2. 系统静音/媒体音量为 0：播报走媒体音量，用户以为静音不影响。
3. TTS 队列：连续触发时后一条会把前一条顶掉，需要排队 + 优先级（结束总结 > 目标达成 > 定时定距）。
4. 蓝牙耳机路由：连着耳机时声音跑到耳机，用户以为没响。

---

## 症状 9：官方 App 下架后数据拿不回来

顺序很重要：**先导出，再换工具**。

1. 旧手机若还能进 App，先导出（截图/Excel/网页后台）。
2. 找历史版本安装包，断网使用避免强制升级。
3. 服务器已停且无本地缓存 → 基本拿不回来，直接转自建方案，别在恢复上耗时间。

---

## 排查记录模板

遇到问题时按这个表填，填完基本就知道卡在哪一层：

| 项 | 填什么 |
| --- | --- |
| 机器型号 / 铭牌参数 | 品牌型号、功率、承重、速度范围 |
| 手机型号 / 系统版本 | 影响权限与后台策略 |
| 症状 | 一句话，可观察的现象 |
| 已排除项 | 面板是否正常、遥控类型、是否有数据 |
| 操作步骤 | 一步一步，每次只改一个变量 |
| 结果 | 现象变化，或「无变化」 |
| 判定层 | 机器 / 遥控 / 连接 / 协议 / 应用 |

## 安全边界

- 任何控制类测试：**空载、低速、松手即停**，人不要站在跑带上。
- 不绕过急停、童锁、安全锁。
- 不在他人设备上做协议逆向或试码。
- 电气改装（换控制板、改供电）找专业维修。
