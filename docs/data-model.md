# 数据模型与聚合口径

这一页定义「一次运动」怎么记、怎么存、怎么汇总。口径定死了，周报和趋势图才不会互相打架。

## 一条运动记录

```json
{
  "id": "r-20261023-0730",
  "startedAt": "2026-10-23T07:30:12+08:00",
  "endedAt": "2026-10-23T08:04:51+08:00",
  "activeSeconds": 1980,
  "pausedSeconds": 120,
  "distanceMeters": 3240,
  "steps": 4360,
  "avgSpeedKmh": 5.9,
  "maxSpeedKmh": 7.2,
  "caloriesKcal": 168,
  "segments": [
    { "kind": "run", "startSec": 0, "endSec": 900 },
    { "kind": "pause", "startSec": 900, "endSec": 960 },
    { "kind": "run", "startSec": 960, "endSec": 1980 }
  ],
  "source": "ble-ct1",
  "note": ""
}
```

字段约定：

| 字段 | 含义 | 说明 |
| --- | --- | --- |
| `startedAt` / `endedAt` | 墙上时间 | 用本地时区带偏移，便于跨时区正确归日 |
| `activeSeconds` | 有效运动秒数 | **不含暂停**，统计一律用它，不用 `endedAt - startedAt` |
| `pausedSeconds` | 累计暂停秒数 | 单独记，用来解释「为什么总时长比运动时长长」 |
| `segments` | 分段 | 暂停也是一段，恢复后接着记，保证时间轴连续 |
| `distanceMeters` / `steps` | 里程与步数 | 设备上报优先；无上报时用速度积分估算，并在 `source` 标注 |
| `source` | 数据来源 | `ble-ct1` 表示设备直连；`manual` 手工录入；`estimated` 估算 |

## 三条容易做错的口径

1. **暂停不进有效时长。** 常见错误是把墙上时间当运动时长，一次 20 分钟的训练中途暂停 5 分钟，记录成 20 分钟，周报就会虚高。
2. **恢复后接着记，不新开一条。** 暂停-恢复属于同一次训练，只在 `segments` 里多一段，不拆记录。拆记录会让「今天跑了几次」变成错误答案。
3. **跨零点按开始日归日。** 23:50 开始、00:20 结束的训练算前一天，否则周报和累计天数会在周末反复对不上。

## 聚合口径

### 单日

- 训练次数：当日记录条数
- 有效时长：当日 `activeSeconds` 之和
- 里程：当日 `distanceMeters` 之和
- 平均配速：总时长 / 总里程，**不是**每次配速的平均值（后者会被短距离训练拉偏）

### 周（自然周，周一为起始）

- 本周训练天数：有记录的**去重日期数**，不是记录条数
- 本周总里程、总时长、平均每次时长
- 与上周对比：只比同期天数内的数据会不会更公平？个人使用建议直接比整周，但要标注「本周尚在进行中」避免误解

### 累计

- 累计跑步天数：全部记录的去重日期数，跨年不清零
- 连续天数（streak）：从最近一次有记录的日子往前数连续天数；当天还没跑时，streak 显示到昨天为止，不提前清零
- 累计里程、累计时长、累计次数

### 趋势

- 按周聚合画折线，而不是按天：日粒度噪声大，个人数据量小的时候周粒度才有形状
- 少于 4 周的样本不画趋势结论，只展示数据点

## 存储建议

- 本地优先：SQLite 或 JSON 文件，字段与上面的结构一致，不要为了 UI 方便改结构
- 导出：直接导出为上面的 JSON 数组，方便换机、备份、给别人复用
- 不要存无关的个人信息：不需要位置、不需要通讯录权限、不需要账号体系也能用
